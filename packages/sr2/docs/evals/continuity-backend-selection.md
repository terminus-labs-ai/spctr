# Continuity Backend Selection — Bakeoff Verdict (sr2-100 / AC19)

**Verdict: NO-GO. No candidate qualifies as the continuity default.** The
lexicographic rule of FR21 eliminated every candidate at stage 2
(*require improved correctness/recall over the full-history baseline*) under
both readings of that clause. Per the spec's Implementation Notes ("Gate later
slices on task 10"), the feature stops before product assembly/cutover and
returns to a spec session with this evidence. `sr2-101` (bounded reason-aware
assembly) and `sr2-166` (live demo gate) stay gated.

Machine-readable report with every raw number:
[`evals/continuity/results/backend-bakeoff.json`](../../evals/continuity/results/backend-bakeoff.json)
(generated by `evals.continuity.runner.run_bakeoff`, no wall-clock input, so
it reproduces byte for byte).

## What ran

Five arms over the fixed versioned corpus (`evals.continuity.scenarios.CORPUS`,
12 scenarios) with the budgets in that file untouched:

| Arm | Path | Delivered background |
|---|---|---|
| `baseline` | `run_baseline` | current full-history behavior (`seed_session` + `turn`) |
| `structured` | `run_candidate("structured")` | `StructuredIndex` |
| `vector_hybrid` | `run_candidate("vector_hybrid")` | `VectorHybridIndex` |
| `graph` | `run_candidate("graph")` | `GraphIndex` |
| `embedding` | `run_candidate("embedding")` | `EmbeddingContinuityIndex` over the committed FR40 vectors |

Every arm uses the deterministic extraction double (no model call), the pinned
price table, and the Metric Contract's latency constant. Each scenario runs
five times. All nine metrics plus `closed_residency` are published per turn.

## Which numbers the gate reads

Both arms publish aggregates, but the two published aggregates are **not**
comparable, and feeding them to the gate would score a scoring-set difference:

* the baseline sweep scores only gold-bearing turns (`gold_turns`);
* a candidate run publishes **every** FR40 turn — including the six turns that
  declare no gold — and an unscored turn is 0 on correctness, and on `recall`
  for the turns before A's decision re-enters the request.

That difference alone accounts for most of the gap below.

The single policy leak and the single stale read are the corpus's planted

arm. Because they are instrumentation rather than backend behavior — and
because FR21 lists them as disqualifiers for *candidates*, measured against
"the current full-history baseline" — the gate compares each candidate
against the baseline's count instead of an absolute zero. The absolutes are
published next to the verdict either way. Under a literal absolute-zero
reading, nothing qualifies either (including the baseline), which strengthens
rather than changes this verdict.

## Why no candidate can beat this corpus

Two independent reasons, both structural.

1. **The baseline sits at the ceiling on ten of twelve scenarios.** Full
   history delivers every declared block, so recall is 1.000 by construction,
   and the only correctness miss in the corpus is the pinned fixture's planted
   stale read. A bounded backend cannot improve a maximum; it can only tie it
   while spending budget to find the material again. Worse, the candidate
   sweeps deliver slightly *more* background than the baseline here
   (7 467–7 476 vs 7 425 tokens) and cost more. Not because retrieval is
   wasteful on the FR31 scenarios — those rows are byte-identical — but
   because the one place a candidate does deliver, the FR40 reference turn,
   publishes every hit the index returns (A's records *and* the unrelated B
   turns), while the baseline's declared context for the same turn is
   smaller: 118 delivered background tokens for repetition 1 against the
   baseline's 56.
2. **Only one scenario consults a candidate index at all.** On the ten FR31
   scenarios and the cage fixture, a candidate run retrieves nothing: it
   delivers background through the same full-history path as the baseline
   (`run_scenario_turn` never receives the index). This is provable from the
   artifacts — those 60 observations are byte-identical to the baseline's in
   all four candidate runs. The only discriminating scenario is
   `episode_close_paraphrase_return`, and there the ordering is:

   | Arm | correctness | recall | background tokens | closed_residency |
   |---|---|---|---|---|
   | baseline | 1.000 | 1.000 | 280 | n/a |
   | structured | 0.400 | 0.400 | 322 | 0 |
   | vector_hybrid | 0.400 | 0.400 | 322 | 0 |
   | graph | 1.000 | 1.000 | 331 | 0 |
   | embedding | 0.400 | 0.400 | 322 | 0 |

So the corpus contains no condition in which bounded retrieval could plausibly
beat replaying everything: no long horizon that overflows the cap, no
retrieval-difficulty gradient, no distractor load the baseline must swallow.
FR21's stage 2 asks a question this benchmark cannot answer in a candidate's
favor.

## Evidence limits found while running (each reproducible)

These are findings about the harness, not verdicts on the backends. They were
discovered by sr2-100 and are filed as follow-up beads; none was repaired in
this slice, because repairing the measurement and adjudicating it in the same
bead would put the verdict past its own evidence.

1. **Candidate index unused on 11 of 12 scenarios.** As above; see
   `_delivery` / `run_scenario_turn`, and confirm by diffing any non-FR40
   scenario's rows between `results/<run-id>/observations.jsonl` from a
   baseline run and a candidate run.
2. **Scoring-set mismatch** between the baseline sweep (gold turns only) and
   the candidate run (all FR40 turns) — the reason the published aggregates
   differ, and the reason the gate reads the gold-turn subset.
3. **Shared index state across repetitions.** `_run_fr40_scenario` builds one
   index per scenario and calls `index.append(records)` once per repetition;
   re-appending the same six record ids creates version chains that push
   distinct records out of `search(limit=6)`. Measured delivered background
   tokens at the reference turn, repetition 1→5: structured, vector/hybrid
   and embedding `118, 69, 45, 45, 45`; graph `118, 69, 48, 48, 48`, with the
   delivered blocks degrading from six distinct records to repeated copies of
   one or two. Consequence: candidate FR40 scores depend on `run_index` — and
   graph's 1.000 there reflects which records survived the crowding (the
   versions it keeps still state the decision string), not a demonstrated
   retrieval advantage. Repetition 1 is the only clean read for every
   candidate, and there the embedding candidate does deliver A's decision, as
   AC27 requires. Related: `test_ac27_r2` is an existential check over the
   whole published run, so one delivering repetition satisfies it; the
   bakeoff scores per repetition. Not a re-adjudication of sr2-163 — a note
   that its evidence is weaker than the bakeoff needs.
4. **Observation key collision**: `turn_index` is a gold-position in the
   baseline arm and an absolute turn index in the FR40 candidate arm;
   `_canonical_rows` normalizes and refuses unknown shapes rather than
   guessing.
5. **Latency carries no signal.** Both arms publish the Metric Contract's
   pinned constant, so FR21's final tie-breaker cannot rank anything; cost and
   token figures do rank, and rank the baseline first.
6. **Selection-predicate wording** (the 2026-11-04 open question) still needs
   an owner ruling; both readings are evaluated in the report.

the Metric Contract.

## What a second bakeoff needs before it can select a backend

Recorded for the spec session this verdict returns to:

1. **Budget pressure on the baseline**: at least one multi-turn, long-horizon
   scenario where full history exceeds the configured cap, so replaying
   everything is actually penalized. FR21's stage 2 is unsatisfiable otherwise.
2. **Real candidate delivery in the sweep** (finding 1): route the FR31
   scenarios' background through the selected index, or drop the pretence that
   those scenarios compare backends.
3. **Per-repetition isolation of candidate indexes** (finding 3) so scores do
   not depend on `run_index`.
4. **A measured latency method for candidates**, or removal of latency from
   the rule as written.
5. **An owner ruling on the qualification predicate**, so the next report
   applies one reading instead of two.

No `configs/*.yaml` change ships with this verdict: with no selected backend,
there is no continuity default to write.
